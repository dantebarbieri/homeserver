# homeserver-nixos

NixOS configuration for **homeserver** — a headless home server that hosts
Docker-based services (see [homeserver-docker](https://github.com/dantebarbieri/homeserver-docker)) with a
[Homer](https://github.com/bastienwirtz/homer) dashboard at
**<https://homer.danteb.com>** (see [homeserver-homer](https://github.com/dantebarbieri/homeserver-homer)).

## Overview

| Item | Value |
|---|---|
| Hostname | `homeserver` |
| IP | `192.168.50.100/24` (static, bonded NICs) |
| OS | NixOS (flake on `nixos-unstable`, pinned by `flake.lock`; `system.stateVersion` 25.11) |
| Shell | Zsh + Zim, configured per user by Home Manager |
| Editor | Neovim ([kickstart.nvim](https://github.com/nvim-lua/kickstart.nvim)) |
| GPU | NVIDIA RTX 2070 SUPER (headless, production driver) |
| Containers | Docker + Docker Compose (auto-updated daily at 04:00) |
| Auth | SSH key-only on port 28; `sudo-rs` (Rust) with asterisk feedback |

## Layout

| Path | Purpose |
|---|---|
| `flake.nix` / `flake.lock` | Entry point. Pins nixpkgs, Home Manager and the nix-index database; builds `nixosConfigurations.homeserver`. |
| `configuration.nix` | Root module: imports `hardware-configuration.nix` and every file in `modules/`. |
| `modules/*.nix` | One concern per file (networking, storage, docker, backups, …). |
| `lib/shared.nix` | Values several modules share: ntfy endpoint, alert scripts, MirkLurk hold. |
| `home/danteb.nix` | Home Manager config for `danteb` (zsh, Zim, git identity/signing). |
| `hardware-configuration.nix` | Generated by `nixos-generate-config`; do not edit by hand. |
| `tests/` | Evaluation-based regression checks (also run in CI). |

`/etc/nixos` on the server is a symlink to this directory, so plain
`nixos-rebuild` finds `flake.nix` and builds `#homeserver` automatically.
Because the flake lives in a Git repository, Nix copies only **tracked** files
into the store: untracked secrets such as `docker/.env` are never read, and a
new module must be `git add`ed before it takes effect.

## Networking

- **Bond** (`bond0`): `enp66s0f0` + `enp66s0f1` in `active-backup` mode.
- **Preferred member**: `enp66s0f1`, set through networkd's `PrimarySlave`
  on `40-enp66s0f1`. The legacy `driverOptions.primary` is not translated
  by NixOS's networkd backend. Applying this setting can change the active link;
  use a maintenance window with console access available.
- **Stack**: `systemd-networkd` + `systemd-resolved` (NetworkManager disabled).
- **IPv6**: SLAAC from router (`2603:8080:1e00:1c97::/64`); stable EUI-64 GUA `2603:8080:1e00:1c97:9e6b:ff:fe45:2bc2`.
- **DNS**: `127.0.0.1` (AdGuard Home), `1.1.1.1`, `8.8.8.8`.
- Boot waits for network readiness (`systemd.network.wait-online`).

## Storage

- **Software RAID** (`mdadm`): array `/dev/md0` with a hot spare; mdadm is
  configured to call `/usr/local/bin/mdadm-ntfy` on events.
- **LVM** enabled in both the running system and the initrd.
- Filesystem tools: `dosfstools`, `xfsprogs`, `parted`.

## GPU (NVIDIA)

The RTX 2070 SUPER runs headless with `nvidiaPersistenced` to keep the GPU
initialized without X11/Wayland. The `nvidia-container-toolkit` is enabled so
Docker containers can access the GPU (used for hardware transcoding and ML
workloads like Immich and Jellyfin).

`plex-hwaccel-check.timer` exercises Plex's CUDA/NVENC path every six hours and
alerts through ntfy if Plex silently falls back to software transcoding.

`services.xserver.videoDrivers = [ "nvidia" ]` is set for driver registration
only — it does **not** enable X11.

## Docker Compose auto-update

A systemd timer (`docker-compose-update.timer`) runs daily at 04:00 (±5 min
jitter). The corresponding oneshot service:

1. Record running image digests for rollback in `/srv/docker/image-snapshots`.
2. `git pull` from `/srv/homeserver`, with automatic Git maintenance kept in
   the foreground so its temporary lock files cannot race the subsequent
   ownership repair. The pull runs as root, so `.git` and every path the pull
   changed (plus the directories containing it) are handed back to
   `danteb:docker`; otherwise a later manual `git pull` fails with
   "Permission denied".
3. Pull non-buildable images with at most four parallel Compose operations,
   rebuild local images, reconcile containers, refresh the custom Prowlarr
   definitions from upstream (`docker/docs/PROWLARR.md`),
   recreate Homepage, and prune unused images/networks.

Failures stop the update and trigger the existing `ntfy-failure@` handler, with
three exceptions: pulled and locally built images are isolated per service. If
the combined pull is exhausted, the job pulls services one at a time; if the
combined build fails, it rebuilds services one at a time. Either way it deploys
everything else, leaves each failing service running its previous container,
and then fails so ntfy still reports it. Likewise, a Prowlarr definition whose
upstream changed shape keeps its installed copy, and the job finishes before
failing.
Combined image pulls get at most three attempts, with 60- and 120-second
delays, before the one-at-a-time fallback. Retries and the fallback mitigate
transient registry throttling (ghcr.io has rejected the large immich CUDA image
with `toomanyrequests` during the parallel pull); they cannot fix invalid
credentials, missing images, or a sustained registry outage. Git uses
`--ff-only`, and automatic
maintenance finishes before ownership repair. The entire job holds
`/run/lock/homeserver-compose.lock`; manual Compose operations do not
automatically honor that lock.

The MirkLurk wiki frontend is in Compose profile `mirklurk-release`, so this
job never starts or recreates it. `mirklurk-auto-update.timer` (04:15, ordered
after this job) builds and deploys eligible MediaWiki base-image updates for it
and alerts only on failure or a stall; see
[MirkLurk wiki](../docker/docs/MIRKLURK.md#automatic-base-image-updates).

A deploy key is auto-generated on first activation at
`/root/.ssh/docker-compose-deploy` — add the public key to GitHub as a
read-only deploy key.

### Docker socket consumers

`docker-socket-consumers.service` follows Docker starts/restarts and serially
recreates only running Homepage and Alloy socket proxies, cAdvisor and VPN
namespace watcher services in project `compose`. File bind mounts can otherwise
retain an obsolete Docker socket, especially on older live-restore generations.
Homepage and Alloy themselves use the proxies over TCP and are not
recreated.

The helper does not start stopped/absent consumers or dependencies, pull/build
images, or prune data. It shares
`/run/lock/homeserver-compose.lock` with the daily updater. Recreation briefly
interrupts selected consumers and applies their checked-out Compose configuration
and local image tags. Failure invokes the existing ntfy handler.

See [Docker socket recovery](../docker/docs/DOCKER-SOCKET-RECOVERY.md) for
selection, locking, limitations and verification.

## NixOS auto-upgrade

Package versions come from `flake.lock`, not from channels. The
[`nixos-flake-update`](../.github/workflows/nixos-flake-update.yml) workflow
runs `nix flake update` daily (07:17 UTC, before the 04:00 Chicago repo pull),
evaluates the system, runs the [regression checks](#local-regression-checks),
and pushes the new lock to `main` only if they pass. The 04:00
`docker-compose-update` pulls it, and the 04:30 `nixos-upgrade` builds
`git+file:///srv/homeserver?dir=nixos&ref=main#homeserver` with
`--no-update-lock-file`, so the server always builds exactly the committed,
CI-checked lock. `ref=main` reads committed content only: uncommitted edits in
the checkout are neither built nor copied into the world-readable Nix store.
Every update is a Git commit, so `git log -p nixos/flake.lock` shows what
changed and when. A failed build alerts through ntfy and leaves the current
generation in place; earlier generations stay in the boot menu.

The job runs as root on the `danteb`-owned checkout, so the system Git config
marks `/srv/homeserver` as a `safe.directory`. Nix evaluates flakes through
libgit2, which otherwise refuses the repository (`sudo` works without it,
because libgit2 accepts a repository owned by `SUDO_UID`).

Because a bot commits to `main` most days, keep the server checkout clean:
push changes from a dev checkout, or commit **and push** anything made on the
server before 04:00. A local edit to `nixos/flake.lock` or an unpushed local
commit makes the nightly `git pull --ff-only` fail, which stops both container
and OS updates until resolved.

The job uses `system.autoUpgrade.operation = "boot"` and
`allowReboot = false`: it builds a generation and selects it for the next boot
without switching the running system. `allowReboot = false` alone does **not**
prevent live activation; the upstream operation defaults to `"switch"`.

Schedule regular maintenance reboots to activate staged OS/security updates.
This keeps NVIDIA userspace and the loaded kernel module on matching versions.
A manual `nixos-rebuild switch` after a lock update can still create a mismatch and is
not a substitute for rebooting after a driver update.

### Is a reboot needed?

```bash
reboot-needed             # Read-only; no sudo required
```

This checks **installed changes waiting for a reboot**, not whether a reboot is
queued or safe to perform. It compares the booted kernel, initrd, kernel modules
(including NVIDIA), and kernel parameters with the selected next-boot generation.
It also detects an inactive system generation staged by `nixos-rebuild boot`.
Kernel/driver changes still count after `nixos-rebuild switch`; a userland-only
switch does not require rebooting merely because the booted generation is older.

The command prints the reasons and exits **0** when no reboot is needed, **1**
when one is needed, or **2** if state is missing/unreadable and it cannot determine
the answer. It does not fetch/build updates, check remote versions, send alerts,
inspect `safe-reboot`'s queue/blockers, or schedule a reboot. There is no uptime
threshold or RAID-idle gate. For userland-only staged changes, rebooting is this
server's activation policy, not a claim that every package technically requires
one. It assumes the normal system profile is the next boot target, not a manual
boot-menu or one-shot override.

When it reports changes, use `sudo safe-reboot` to queue a backup-aware reboot;
`sudo safe-reboot --check` separately shows whether it could proceed right now.

`modules/reboot-reminder.nix` uses this same command daily at 10:00 and sends an
ntfy "Reboot needed" notice when installed changes are waiting. Unlike the
interactive check, the reminder stays quiet for the first
7 days after a boot (the upgrade stages something most nights) and holds back while
`md0` is running a scrub or rebuild, so it never invites a reboot that would cut
one short (see below). It repeats daily while changes still need a reboot.

### Safe reboot

Use the Nix-managed command instead of `sudo reboot`:

```bash
sudo safe-reboot           # Queue now; wait as long as needed, even after SSH disconnects
sudo safe-reboot --check   # Dry run: list every blocker without queuing a reboot
sudo safe-reboot --status  # Service state and recent progress
sudo safe-reboot --cancel # Cancel while still waiting; restore previously active timers
```

`--check` needs sudo, exits **0** when nothing would stop a reboot and **1**
otherwise, and prints every blocker instead of stopping at the first:

- `Waiting for: …` — what the queued worker would wait out: busy backup/maintenance
  jobs, a RAID scrub/recovery, the Compose or wiki-backup lock, the deployment hold.
- `Would refuse to reboot: …` — what would make it fail: a failed job, an unreadable
  or degraded RAID, Docker live-restore enabled, an unhealthy wiki SQL backup, or a
  logind shutdown inhibitor the final reboot call would deny (see below).

It changes nothing; it only try-locks the Compose lock and wiki backup directory
and releases them at once. The MirkLurk backup sidecar's first dump after a host boot
can race `mirklurk-db` and fail, so `--check` can report the wiki SQL backup as
unhealthy for about five minutes after every boot until the sidecar's retry succeeds.

`configuration.nix` imports `modules/safe-reboot.nix`, which installs the command
and an **on-demand**, root-owned `safe-reboot.service`. Nothing queues a reboot at
boot or on a schedule. The reminder includes the command.

The worker pauses only currently active (or queued) backup/maintenance timers,
and temporarily guards their services against new starts. It does **not** stop
running jobs. It waits for database/Vaultwarden backups, both offsite syncs,
Docker and NixOS updates, wiki snapshots/deployments/checks/sitemap jobs, socket
reconciliation, and RAID scrub/recovery. It respects the existing wiki deployment
hold without removing it. An idle degraded array, failed job, missing/unreadable
state, stale/failed wiki SQL backup, or Docker/API error refuses the reboot and alerts via the existing ntfy
failure handler. Review and fix a failed job before clearing its failed state.
Backup target failures now return a failing service result, not just an alert.

Once idle, it holds the existing Compose lock and an exclusive lock on the wiki
backup directory, checks again, and requests an orderly reboot directly through
logind's `RebootWithFlags` with `SD_LOGIND_ROOT_CHECK_INHIBITORS`. Shutdown
`block` inhibitors are respected even as root (`systemd-inhibit --list`), as
are other users' `block-weak` inhibitors. Root-owned `block-weak` inhibitors
retain logind's same-owner exemption; root jobs needing protection must use
`block`. Delay inhibitors retain logind's normal grace period.
Logged-in users, including the SSH session that queued it, do not block it.
An inhibitor denial or logind/bus error fails the request and restores timers;
there is no unchecked `systemctl reboot` fallback.
The wiki SQL sidecar takes a shared lock on that same directory,
so existing dumps finish and new dumps wait through Docker shutdown. No container
is manually stopped or removed by the command, preserving `unless-stopped`
restart behavior and existing manually stopped containers.

Docker live-restore is **disabled** so dockerd actually shuts down containers.
Its default per-container stop grace is 180 seconds (Docker 29.9.2 in the pinned
flake supports `default-stop-timeout`); explicit container timeouts, including
Minecraft's 150 seconds, still take precedence. The daemon gets 200 seconds and
systemd allows 240 seconds for cleanup. A stuck container can still be killed at
its timeout. **Docker daemon restarts now interrupt containers too.**

Cancel/failure restores only timers this request paused; it never enables a
disabled timer or clears someone else's deployment hold. A failed restoration
keeps its recovery record under `/run/safe-reboot`; retry `--cancel` after fixing
the systemd error. Cancellation is too late once shutdown is requested. The
queue and guards are volatile and do not survive an actual reboot.

This is not a guard around plain `reboot`, power loss, arbitrary manual jobs, game
sessions, streams, or transcodes. Finish untracked work before queuing. Existing
systemd jobs remain running when their new guard is installed, but **the initial
configuration switch changes Docker settings and can restart Docker**: first let
backups/maintenance finish and arrange a service downtime window. The updated
wiki backup script must also be deployed, with any old in-flight dump finished,
before using this command. Do not run `nixos-rebuild switch` during a queued
reboot; cancel first. Subsequent queued reboots need no SSH session kept open.

The RAID scrub service is not restarted when its definition changes during a
manual switch. Its existing monitor and suppression sentinel remain alive until
the kernel finishes the check; script changes take effect on the next run.
If started while a parity check is already running, the new monitor attaches to
that check without writing a second `check` request. It refuses competing RAID
actions such as recovery/reshape and fails explicitly if a new check does not
start within 30 seconds. Mismatches, unreadable/invalid results, and notification
HTTP failures are reported as failed units through the existing ntfy handler.

Do not reboot or manually interrupt a running scrub expecting its monitor to
prove full completion afterward. A transition to idle and a zero mismatch count
alone cannot distinguish a completed check from an externally canceled one.
Finish the active check before rebooting, or deliberately arrange a fresh full
check after the maintenance reboot.

## Retired terminal mail and calendar

The server no longer installs aerc, khard, khal, vdirsyncer or aerc's w3m helper.
The login calendar and `vdirsyncer-sync` service/timer have been removed.
Existing credentials, downloaded mail, contacts, calendars and sync state are
not deleted. The general-purpose `pass` tool and GPG support are retained.
`mail-config/` remains an optional portable setup, not an active NixOS integration.

## Security

- **SSH**: key-only authentication on port 28; root login disabled.
- **Privilege escalation**: `sudo-rs` (memory-safe Rust implementation) for
  the `wheel` group with `SETENV`; classic `sudo` and `doas` are disabled.
  Provides credential caching and asterisk password feedback by default.
- **Git commits** are signed with SSH keys (`gpg.format = ssh`), configured in
  Home Manager.

## Home Manager

[Home Manager](https://github.com/nix-community/home-manager) runs as a NixOS
module (`modules/home-manager.nix`), so `danteb`'s dotfiles are built and
activated with the system by `home-manager-danteb.service`, with no separate
`home-manager switch`. `home/danteb.nix` manages:

- `~/.zshrc`, `~/.zshenv`, `~/.zprofile`: history, keymap, Zim, zoxide, iTerm2
  integration. System-wide shell setup (aliases, `dc*`/`ns*` functions,
  fastfetch) stays in `modules/shell.nix` for every user. On initial shells,
  fastfetch uses ZSH's current terminal width (`COLUMNS`): below 96 columns the
  logo sits above the info; wider or unknown widths keep the default layout.
- `~/.zimrc`: the Zim module list. Editing it rebuilds `~/.zim/init.zsh` on the
  next shell. zimfw itself comes from nixpkgs, so update it with the flake lock;
  `zimfw upgrade` cannot write to the store.
- `~/.config/git/config`: name, email and SSH commit signing. The system
  `/etc/gitconfig` keeps only machine-wide defaults.

Everything in `home/` is copied into the world-readable Nix store and is
public in this repository. **Never put secrets there.** Keep them in untracked
files that the managed dotfiles source when present:

| File | Loaded by | Use for |
|---|---|---|
| `~/.zprofile.local` | login shells | API keys, tokens and other exported secrets |
| `~/.zshrc.local` | interactive shells | machine-specific interactive tweaks |

Make both `chmod 600`. Because `backupFileExtension` is set, Home Manager moves
a conflicting unmanaged file to `<name>.hm-backup` instead of failing.

### First activation (one time)

Do this the day the change merges. Until the new generation is active, the
old nightly `nixos-upgrade` fails on the flake (root lacks the
`safe.directory` entry) without changing anything; it has no failure alert
yet, so this failure is silent.

```bash
z /srv/homeserver && git pull
# Move secrets out of the soon-to-be-managed ~/.zprofile first.
[ -e ~/.zprofile ] && mv -n ~/.zprofile ~/.zprofile.local && chmod 600 ~/.zprofile.local
sudo nixos-rebuild switch
```

The first lock pins the nixpkgs revision the server already ran, so `switch`
only adds Home Manager. If CI has bumped the lock since, use `boot` and reboot
instead. Home Manager then replaces `~/.zshrc` and `~/.zimrc` and keeps the
old copies as `*.hm-backup`. Open a new shell to check it, then delete the
backups and the now-redundant `~/.gitconfig` once satisfied.

## Neovim / Kickstart.nvim

All [kickstart.nvim external dependencies](https://github.com/nvim-lua/kickstart.nvim#install-external-dependencies)
are installed: `git` (via `programs.git`), `make`, `unzip`, `gcc`, `ripgrep`,
`fd`, and `tree-sitter`.

### Why `neovim` is not in `environment.systemPackages`

`programs.neovim.enable = true` already adds the **wrapped** Neovim
(`finalPackage`) to the system PATH. Listing `pkgs.neovim` again would install
the **unwrapped** copy alongside it.

- [NixOS neovim module source](https://github.com/NixOS/nixpkgs/blob/master/nixos/modules/programs/neovim.nix)
- [NixOS Wiki — Neovim](https://wiki.nixos.org/wiki/Neovim/en)

### Clipboard (SSH / headless)

No `xclip` or `xsel` is installed. Neovim 0.10+ detects SSH sessions and uses
[OSC 52 escape sequences](https://neovim.io/doc/user/provider.html#clipboard-osc52)
natively — no X11 required on the server side.

### Nerd Font

Nerd Fonts are rendered by the SSH **client's** terminal emulator, not the
server. Install a [Nerd Font](https://www.nerdfonts.com/) on your local
machine. `kickstart.nvim` already sets `vim.g.have_nerd_font = true`.

## Applying changes

Commit (or at least `git add`) changes first; the flake ignores untracked files.
A manual rebuild through `/etc/nixos` builds the working tree, so it does copy
uncommitted edits to tracked files (anywhere in the repo) into the Nix store:
check `git status` for stray secrets first.

```bash
sudo nixos-rebuild switch            # activate now
sudo nixos-rebuild boot              # stage for the next boot (preferred for driver/kernel changes)
gh workflow run nixos-flake-update.yml   # lock bump now (otherwise nightly)
```

Don't run `nix flake update` on the server: a locally modified `flake.lock`
blocks the nightly pull (see [auto-upgrade](#nixos-auto-upgrade)). To bump by
hand, do it in a dev checkout and push.

Skip `--upgrade`: it only refreshes the root `nixos` channel, which the flake
ignores. After activation, `nix shell nixpkgs#…` and `<nixpkgs>` also resolve
to the locked nixpkgs.

`nix-locate` (and the `nwp` helper built on it) reads the prebuilt database from
[nix-index-database](https://github.com/nix-community/nix-index-database). It is
pinned in `flake.lock` and refreshed by the nightly bump, so the server builds no
index of its own and `~/.cache/nix-index` is unused.

## Forgejo Actions host runner

`services.forgejo-runner.instances.worldforge` runs the `worldforge-host:host`
runner for WorldForge jobs that need `nix develop`. Docker-label jobs use the
Compose runner in `docker/compose.git.yml` instead.

| Item | Value |
|------|-------|
| Unit | `forgejo-runner-worldforge.service` |
| User | static `forgejo-runner` (not `DynamicUser`; see `modules/forgejo-runner.nix`) |
| State / `$HOME` | `/var/lib/forgejo-runner/worldforge` |
| Token file | `/var/lib/forgejo-runner-worldforge.token` (root, `0600`, raw runner token) |
| Runner UUID | `server.connections.default.uuid` in `modules/forgejo-runner.nix` |

The UUID identifies the runner, like a username. The token is its password, and
`forgejo-runner` rejects a `TOKEN=` prefix. Labels come from `modules/forgejo-runner.nix`;
the runner name (`homeserver-worldforge`) exists only in Forgejo.

The runner previously used the retired `services.gitea-actions-runner` module
(`gitea-runner-worldforge.service`, `/var/lib/gitea-runner/worldforge`).
`forgejo-runner-worldforge-migrate.service` runs before the runner while the old
`.runner` file exists. It writes that file's runner token to the token file,
moves the old caches to the new state directory, and removes the old
registration files. `forgejo-runner` refuses to start when a `.runner` file
coexists with configured connections. The runner keeps its Forgejo identity
without re-registration.

```bash
systemctl status forgejo-runner-worldforge
journalctl -u forgejo-runner-worldforge-migrate -u forgejo-runner-worldforge -b
```

## Local regression checks

With Python 3, Bash, jq, and Nix (flakes enabled) available:

```bash
python3 -B -m unittest discover -s nixos/tests -p 'test_*.py'
```

Run from the repository root (on the server, wrap it in
`nix shell nixpkgs#python3 nixpkgs#jq -c …`). This evaluates the flake's NixOS and Home Manager options and exercises scrub,
update, reboot-reminder, safe-reboot and plex-album-check success/failure paths with mock commands; it does not contact or modify the
server, synchronize real data, or build a system closure. The
[`nixos-validate`](../.github/workflows/nixos-validate.yml) workflow runs it,
plus a toplevel evaluation against the committed lock, on every change under
`nixos/`.

The opt-in real-logind regression runs in an isolated NixOS test VM (requires
Linux/KVM), not on the host. It checks root/user-owned block inhibitors,
user-owned weak inhibitors, that `safe-reboot --check` agrees with the real
reboot call for each of them, timer recovery, and a successful guest reboot with
another user and a root-owned weak inhibitor present:

```bash
nix build --impure --no-link --expr '
  let flake = builtins.getFlake ("git+file://" + toString ./. + "?dir=nixos");
  in import ./nixos/tests/safe-reboot-logind.nix {
    pkgs = flake.nixosConfigurations.homeserver.pkgs;
  }'
```
